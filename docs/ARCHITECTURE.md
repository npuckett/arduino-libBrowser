# Architecture

Canonical technical reference for the Arduino Library Browser system. This document describes how data flows from upstream sources through the pipeline into static JSON artifacts consumed by the front-end. It is the first stop for maintainers (human or AI) trying to understand the system without reading code.

## Goals

- Mirror the canonical Arduino library registry into a static, browseable catalog.
- Track new, updated, and removed libraries across versions.
- Enrich each library with GitHub metadata (stars, forks, language, last-updated).
- Surface curated discoveries on the home page via three coordinated pick streams.
- Operate as a low-maintenance, fully automated pipeline (cron-driven, idempotent).
- Publish the result as a static site with no build step.

## Non-goals

- Real-time data. Cron cadence is hourly at best.
- Library installation / package management. The site is a catalog, not a registry proxy.
- User accounts, favorites, or persistence on the client.
- Server-side rendering. Everything is static JSON + browser JS.
- Replacing the official Arduino library manager.

The pipeline is the only mutator of `output/*.json` and `state/sync-state.json`. The front-end is read-only over those JSON files.

## Data sources

Listed in priority order for what the pipeline reads.

1. **`downloads.arduino.cc/libraries/library_index.json.gz`** — primary source.
   - Canonical Arduino release index: one entry per `library.properties` release.
   - Refreshed upstream ~hourly.
   - Fetched with conditional GET (`If-None-Match` ETag + `If-Modified-Since`).
   - 304 means nothing changed and the run exits 0.
   - Implementation: `pipeline/src/sources/arduino-index.ts:fetchArduinoIndex`.

2. **`api.github.com/repos/{owner}/{repo}`** — secondary enrichment.
   - Adds `github_stars`, `github_forks`, `github_language`, `github_updated_at`.
   - Authenticated via `GITHUB_TOKEN` (5,000 req/h).
   - Per-repo ETags stored in `state/sync-state.json` (`repoEtags`).
   - Most libraries hit 304 daily; only repos whose metadata changed incur cost.
   - Implementation: `pipeline/src/sources/github-meta.ts:enrichWithGithub`.

3. **`editors.json`** — manual editor picks. PR-editable. Read by the stats tier.
4. **`themes.json`** — themed auto-pick criteria. PR-editable. Read by the stats tier.

Note: the README mentions the Arduino `library-registry/repositories.txt` as the historical entry point. The current pipeline uses the gzipped `library_index.json.gz` instead because it carries `library.properties` metadata directly and removes a separate parsing step.

## Output artifacts

All four live under `output/` and are regenerated by the pipeline. They are version-controlled so that Pages can serve them straight from the repo root.

| File | What it contains | Reader | Cadence | Approx size |
|------|------------------|--------|---------|-------------|
| `output/libraries.json` | Full catalog (one entry per repo, latest version). Schema v2. | Frontend | Updated by `sync` and `enrich`; written by `buildLibrariesJson`. | ~15 MB |
| `output/changes.json` | This-run delta: `new_libraries`, `updated_libraries` (with `old_version`/`new_version`), `removed_libraries`. | Frontend (home page + computed picks) | Each `sync` run that detects change. | <1 MB |
| `output/stats.json` | Aggregate statistics: `categories` counts, `trending`, `hidden_gems`, `most_depended_on`, `forgotten_classics`, plus `activity` (`daily[]` / `weekly[]` / `categories_top[]` for the home-page Activity section). | Frontend | Weekly (`stats` tier). | <1 MB |
| `output/picks.json` | Curated discoveries payload: `editors`, `themes` (id -> Library[]), `computed` (`new_this_week`, `updated_this_week`, `hidden_gems`, `trending`, `forgotten_classics`). | Frontend (home page Curated Discoveries). | Weekly. | <1 MB |

State: `state/sync-state.json` is the pipeline's persistent working memory (ETags, first-seen-at map, version history). It is not read by the front-end.

## Pipeline structure

Three cron tiers, each implemented as a separate GitHub Actions workflow. The split exists so the cheap hourly fetch can run often without exhausting the GitHub API budget, while the expensive full GitHub refresh runs only once a day.

| Tier | Cron | Workflow | Command | Purpose |
|------|------|----------|---------|---------|
| Hourly sync | `0 * * * *` | `hourly-sync.yml` | `pnpm pipeline:hourly` → `sync` | Fetch `library_index.json.gz` with ETag; if changed, diff + enrich new libs and emit `libraries.json` + `changes.json`. |
| Daily enrich | `0 6 * * *` | `daily-enrich.yml` | `pnpm pipeline:daily` → `enrich` | Refresh GitHub metadata for libraries with stale per-repo ETags. |
| Weekly stats | `0 4 * * 0` | `weekly-stats.yml` | `pnpm pipeline:weekly` → `stats` | Recompute `stats.json` and `picks.json` (editors + themes + computed). |
| Test on PR | on PR / push to main | `test.yml` | `pnpm test` and `pnpm test:e2e` | Typecheck, lint, Vitest unit, Playwright E2E. |
| Pages deploy | on `workflow_run` success / push to main | `pages.yml` | upload + deploy | Publish the repo as the GitHub Pages artifact. |

CLI subcommands (see `scripts/pipeline.ts:parseCli`):

- `sync`    — fetch upstream, refresh libraries/changes.
- `enrich`  — refresh GitHub enrichment metadata (ETag-aware).
- `stats`   — compute trending + curated picks.
- `all`     — run `sync` → `enrich` → `stats` sequentially.
- Flags: `--dry-run`, `--verbose`, `--full` (sync only: re-enrich everything ignoring ETags).

Exit codes:

- `0` — success (including no-op runs).
- `1` — retryable transient error.
- `2` — configuration error (do not retry).

`pages.yml` is wired with `workflow_run` so that any successful sync/enrich/stats run triggers a Pages deploy. Direct pushes to `main` also deploy. The deploy workflow uses `actions/upload-pages-artifact` with `path: '.'` — the entire repo root is the published site.

## Change detection algorithm

Defined in `pipeline/src/transforms/diff-detector.ts`.

The Arduino index contains one entry per release (every tagged version in the registry). The pipeline collapses those to **one Library per repository**, keeping the highest version per repo (loose semver compare; returns 0 on unparsable strings).

Each release is fingerprinted with a short SHA:

```
sha = sha256Short( archiveFileName + "|" + version )
```

Detection rules applied per repo, against state:

- **New**: `state.firstSeenAt[repoName]` is missing. The repo is added to `newLibs`; `firstSeenAt` is set to `now`; a one-entry `version_history` is seeded; `lastSeenSha` and `previousVersion` are recorded.
- **Updated**: `state.firstSeenAt[repoName]` exists but `state.lastSeenSha[repoName]` differs from the freshly computed `sha`. A `{ version, seen_at }` entry is appended to `version_history`; `lastSeenSha` and `previousVersion` are updated; the lib is added to `updatedLibs` with `previous_version` set to the prior version.
- **Unchanged**: SHAs match. The lib is skipped and carried over from `libraries.json`.
- **Removed**: a repo previously in `libraries.json` is not present in the upstream latest-set. Its `repository_name` is appended to `removed`.

State side effects are written in-place; `state.lastHighWaterMark` is bumped to `now.toISOString()` on every successful detection pass. `state.knownLibraryCount` reflects the new total.

### V1.5 → V2 migration

The pipeline reads `output/libraries.json` on every run. Older `libraries.json` files were produced by the legacy v1.5 PowerShell pipeline and lack V2 fields (`first_seen_at`, `last_seen_sha`, `version_history`, `release_count`). The reader at `scripts/pipeline.ts:readPreviousLibraries` always passes the loaded array through `migrateLibraries` (`pipeline/src/transforms/v1-to-v2-migration.ts`). Detection: a record is treated as v1.5 if it lacks all four V2 fields OR has string-typed `architectures` or `depends`. v1.5 records are reconstructed with:

- `first_seen_at` from the earliest of `processed_at`, `enhanced_at`, `enhancement_date`, or `now`.
- `last_seen_sha` from `sha256Short("<name>-<version>.zip" + "|" + version)`.
- `version_history` as a one-entry list with the existing version.
- `architectures` and `depends` parsed from comma-separated strings, with version constraints (e.g. `Wire (>=1.0)`) stripped to bare names.

`seedStateFromLibraries` then hydrates the empty state with the migrated values, so the next `sync` does not redundantly re-mark every library as updated.

A safety net in `runSync` (`scripts/pipeline.ts:runSync`, the `previousByRepo` block) preserves prior `github_*` enrichment for libs that were reconstructed from upstream but lack fresh cache data, until the next daily enrich run refreshes them.

## Schema versioning

Two schemas coexist.

- **v1.5 (legacy)** — produced by the old PowerShell pipeline. No `version` field on the file; `architectures` and `depends` are comma-separated strings; no `first_seen_at`, no `last_seen_sha`, no `version_history`. Frontend is tolerant: `archsToArray` (in `index.html`) splits both shapes.
- **v2 (current)** — produced by `pipeline/src/output/build-libraries-json.ts`. Top-level: `{ version: 2, enhanced_at, total_libraries, index_etag, index_last_modified, libraries, stats }`. Each Library: `first_seen_at`, `last_seen_sha`, `version_history`, `release_count`, `previous_version?`, `architectures: string[]`, `depends?: string[]`, plus optional GitHub fields.

Migration is one-way: `migrateLibraries` reads v1.5 and emits v2; the writer only emits v2. Once the in-repo `libraries.json` is v2 the migration is a no-op.

The front-end checks for v2 fields (`first_seen_at`, `last_seen_sha`, etc.) and uses them when present; otherwise it falls back to v1.5 shape so the site renders either schema without crashing.

## Curated Picks system

Three streams, merged into `output/picks.json` by `pipeline/src/output/build-picks-json.ts:buildPicksJson`.

1. **Editor Picks (manual, PR-driven).**
   - Source: `editors.json` at the repo root, shape `{ editors: Editor[] }`.
   - Each `Editor` has `id`, `name`, `url`, `bio`, and a `picks` array of `{ library, picked_at, note? }`.
   - The pipeline preserves `picks` exactly — they are never overwritten. Order is "newest `picked_at` first".
   - To add an editor: append to the array and open a PR. No pipeline changes required.

2. **Themed Auto-Picks (declarative, self-rotating).**
   - Source: `themes.json` at the repo root, shape `{ themes: Theme[] }`.
   - Each `Theme` has `id`, `title`, `criteria` (`categories_any?`, `architectures_any?`, `min_stars?`, `exclude_categories?`), and `count`.
   - Selection: `pipeline/src/transforms/theme-picker.ts:pickByTheme` applies the criteria over `libraries[]`, then ranks and returns up to `count`.
   - Themes are deterministic given library data; rotation comes from natural library churn week to week.

3. **Computed Picks (algorithmic).**
   - `new_this_week` — top 8 from `changes.json.new_libraries` (sorted by name).
   - `updated_this_week` — top 8 from `changes.json.updated_libraries` (shows old → new version).
   - `hidden_gems` — `pipeline/src/transforms/computed-picks.ts:hiddenGems` (low stars, recently updated, has description).
   - `trending` — `pipeline/src/transforms/computed-picks.ts:trending` (7-day star deltas).
   - `forgotten_classics` — `pipeline/src/transforms/computed-picks.ts:forgottenClassics` (high stars, no update in >365 days).
   - `most_depended_on` lives in `stats.json` rather than `picks.json`.

`picks.json` shape:

```
{
  generated_at: string,
  editors: Editor[],
  themes: Record<themeId, Library[]>,
  computed: {
    new_this_week: Library[],
    updated_this_week: { library: Library, old_version, new_version }[],
    hidden_gems: Library[],
    trending: Library[],
    forgotten_classics: Library[]
  }
}
```

## Frontend

Static HTML/CSS/JS. No build step. The repo root is the GitHub Pages artifact.

- `index.html` — single-file app with embedded `<script>`; contains rendering, sort modes, search, modal detail view, and pick-stream rendering. Tolerates both v1.5 and v2 `libraries.json` shapes.
- `style.css` — plain CSS, no preprocessor.
- `output/*.json` — data files, served verbatim.
- Client-side fuzzy search reuses `pipeline/src/transforms/fuzzy-search.ts` algorithms ported into the page (Levenshtein, synonyms, did-you-mean).

E2E tests (`tests/e2e/`) use `global-setup.ts` to swap in a 12-library fixture (`tests/e2e/fixtures/libraries.v2.json` + a small `picks.json`) before the suite runs, then `global-teardown.ts` restores originals. The fixture path is what `globalSetup`/`globalTeardown` reference — do not move it without updating both.

## State management

`state/sync-state.json` (`SyncState` type in `pipeline/src/types.ts`) is the pipeline's persistent memory. Fields:

- `lastEtag` / `lastModified` — upstream index conditional-GET validators.
- `repoEtags: Record<repoName, etag>` — per-repo GitHub ETags.
- `lastHighWaterMark: string` — ISO timestamp of last detection pass; used as `changes.json`'s `since` anchor.
- `knownLibraryCount: number` — count from the most recent sync.
- `firstSeenAt: Record<repoName, ISO>` — when each repo first appeared.
- `lastSeenSha: Record<repoName, sha>` — most recent release fingerprint per repo.
- `previousVersion: Record<repoName, version>` — version seen in the previous sync.
- `versionHistory: Record<repoName, { version, seen_at }[]>` — every release we've seen.

Persistence is atomic: `pipeline/src/utils/state.ts` writes to `<path>.tmp` and renames. The file is created on first run if missing.

The pipeline is **idempotent**. Running `sync` twice with no upstream change returns 304 and writes nothing. Running `enrich` with up-to-date per-repo ETags returns 304 per repo and writes nothing. This is what makes the hourly cron cheap.

## Performance

- **API calls per quiet day (hourly tier only):** ~24 (one per hour, almost all 304).
- **API calls per enrich day:** ~50-200 GitHub calls (most repos 304). The bulk of the catalog hits 304; only repos whose GitHub metadata changed since the last visit cost a 200.
- **First-time run (cold start):** ~9,600 GitHub calls — one per library. Subsequent runs collapse rapidly because ETags populate per-repo.
- **Daily GitHub budget:** 5,000/hour, 180,000/month. The pipeline stays well under.
- **Pipeline duration:** `sync` ~5-15 min; `enrich` ~15-30 min; `stats` minutes. Timeouts are 15 / 60 / 120 min respectively.
- **Concurrency controls:** each workflow uses `concurrency: { group: <name>-${{ github.ref }}, cancel-in-progress: true }` so a long run doesn't queue behind itself.
- **Static site load:** under 2 s; client-side filtering and sorting.

## Failure modes

- **404 on GitHub** — counted (`metrics.notFound`), the repo's cache entry is nulled, and the library is enriched with whatever was already in `libraries.json`. The run continues.
- **Rate limit (403 with `x-ratelimit-remaining: 0`, or 429)** — `parseRateLimitReset` reads `x-ratelimit-reset` and the pipeline `sleep`s until that epoch + 1 s, then retries. After `maxRetries` (default 3) the offending repo throws; that error is caught at the per-repo boundary in `enrichTargets` and logged as a warning so one bad repo does not fail the whole run.
- **Network / transient error** — exponential backoff, `1000 * 2^(attempt-1)` ms, up to `maxRetries`.
- **Upstream index schema change** — `fetchArduinoIndex` throws (`Unexpected response fetching Arduino index: status=...`) and `runSync` wraps it in `RetryableError`. The workflow exits with code 1 and the run is logged.
- **Missing `libraries.json` when running `enrich`/`stats`** — `loadLibrariesOrFail` throws `ConfigError`; workflow exits with code 2.
- **Corrupt `editors.json` / `themes.json`** — `readEditorsFile` / `readThemesFile` catch and return empty arrays, so a bad file degrades gracefully rather than failing the run.
- **Signal during run** — SIGINT/SIGTERM exit with code 130 after a warn log.

## Design choices

### Why `library_index.json.gz` instead of `repositories.txt`?

`repositories.txt` is a flat list of repo URLs; each would require a separate clone/parse step to extract `library.properties`. `library_index.json.gz` is one fetch that already contains every release's parsed metadata, in a stable schema, and ships with a CDN-backed ETag. One HTTP round-trip replaces thousands.

### Why ETag instead of full polling?

The Arduino index changes ~hourly but is mostly static between changes. Polling always returns the full multi-megabyte payload. Conditional GET returns 304 with no body most of the time, which is what makes the hourly cron cheap and the pipeline idempotent. The same reasoning drives per-repo ETags against the GitHub API: most repos do not change daily, so 304 is the common case.

### Why per-repo ETag for GitHub?

GitHub does not provide a "list all my libraries' metadata" endpoint, and there is no aggregate ETag for many repos at once. Each repo must be fetched individually. Storing the ETag per repo lets us revalidate only what could have changed and skip the rest with a 304.

### Why tsx / Node `--experimental-strip-types` (not a TS compiler)?

The pipeline is plain TypeScript with `.js` extensions in import specifiers so Node 20's built-in type-stripping runs the source directly. No transpile step means no artifact to publish, no separate dev/prod builds, and the GitHub Actions runner uses the same Node invocation as local. The README's `--experimental-strip-types` flag was superseded by Node's built-in TS support; the package.json scripts use whichever invocation is current.

### Why schema v2 (vs keeping v1.5)?

v1.5 had no stable identity for a release, so detecting "this is a new version" required recomputing everything every run. v2 adds `last_seen_sha` (cheap diff), `version_history` (we know what versions we've seen), `first_seen_at` (when a library entered the catalog), and `release_count`. The schema also normalizes `architectures` and `depends` to arrays, which the v1.5 comma-string format kept tripping parsers on.

### Why `editors.json` is editable but `picks.json` is generated

`picks.json` is a derived view over `libraries.json` + `editors.json` + `themes.json` + `changes.json`. Letting humans hand-edit it would conflict with the next pipeline run. Manual editorial content goes in `editors.json` (and themed criteria in `themes.json`); the pipeline is the single source of truth for assembling the display list. This keeps the PR surface small and prevents stale picks.
