# Curated Picks

The home page's **Curated Discoveries** block surfaces three coordinated pick streams, all generated by the weekly stats pipeline and emitted to `output/picks.json`.

See [README.md → Curated Discoveries](../README.md#curated-discoveries) for the high-level overview. This document is the full reference: schemas, pipeline mechanics, copy-paste recipes, on-page rendering, and FAQ.

| Stream | Source of truth | Updated by | Display location |
|---|---|---|---|
| Editor Picks | [`editors.json`](../editors.json) | PR (human) | `#editorPicksRow` |
| Themed Auto-Picks | [`themes.json`](../themes.json) | Weekly pipeline | `#themedRows` (one row per theme) |
| Computed Picks | `output/libraries.json` + `output/changes.json` | Weekly pipeline | `#computedRow` |

---

## Stream 1: Editor Picks (manual, PR-editable)

### What it is

Human-curated picks from named editors. The pipeline reads `editors.json` verbatim — **your `picks: [...]` arrays are never overwritten by automation**. Anyone can add themselves via PR.

### File: `editors.json` (project root)

Schema (see `pipeline/src/types.ts` lines 87-99):

```ts
interface Editor {
  id: string;          // URL-safe handle, used as DOM id suffix
  name: string;        // Display name
  url: string;         // Link target (usually a GitHub profile)
  bio: string;         // One-line description
  picks: EditorPick[];
}

interface EditorPick {
  library: string;     // Must match libraries.json `name`, case-insensitive
  picked_at: string;   // ISO date (YYYY-MM-DD); drives display order
  note?: string;       // Shown in the library detail page
}
```

Live example from the current `editors.json`:

```json
{
  "id": "knolleary",
  "name": "Nick O'Leary",
  "url": "https://github.com/knolleary",
  "bio": "Author of PubSubClient and co-creator of Node-RED. IoT and MQTT enthusiast.",
  "picks": [
    {
      "library": "PubSubClient",
      "picked_at": "2025-10-03",
      "note": "The lightweight MQTT client I wrote — still the simplest way to talk to a broker."
    },
    {
      "library": "Arduino_JSON",
      "picked_at": "2026-02-14",
      "note": "Straightforward JSON encode/decode for tiny payloads."
    }
  ]
}
```

### How to add yourself as an editor

Open `editors.json` and append a new entry to the `editors` array. Copy-paste template:

```json
{
  "editors": [
    ... existing editors ...,
    {
      "id": "your-handle",
      "name": "Your Name",
      "url": "https://github.com/your-handle",
      "bio": "What you build. (one sentence)",
      "picks": [
        {
          "library": "LibraryName",
          "picked_at": "2026-06-30",
          "note": "Why this library is special."
        }
      ]
    }
  ]
}
```

Validation lives entirely in the frontend lookup at `index.html:1141-1145` — there is no build-time schema check. Keep these rules in mind:

- `id` — lowercase, alphanumeric + dashes. Becomes a DOM id fragment, so avoid spaces or punctuation.
- `library` — must equal `name` in `output/libraries.json`, case-insensitive. Use the exact canonical name; the matching code lowercases both sides (`index.html:1142`).
- `picked_at` — ISO date `YYYY-MM-DD`. Used for newest-first ordering within your `picks` array.

### How to add a new pick (to an existing editor)

Find your editor in `editors.json` and append to their `picks` array:

```json
{
  "id": "knolleary",
  "name": "Nick O'Leary",
  "url": "https://github.com/knolleary",
  "bio": "Author of PubSubClient and co-creator of Node-RED. IoT and MQTT enthusiast.",
  "picks": [
    ... existing picks ...,
    {
      "library": "PubSubClient",
      "picked_at": "2026-06-30",
      "note": "Still my daily driver for MQTT — version 2.8 bumped keepalive handling."
    }
  ]
}
```

The newest `picked_at` you have becomes the card shown on the home page. Older picks remain in the array (the pipeline preserves them) and surface in the per-editor history on the library detail page.

### How the pipeline handles it

`buildPicksJson` reads `editors.json` on each weekly run ([`build-picks-json.ts:38-56`](../pipeline/src/output/build-picks-json.ts)). The whole file is forwarded as `picks.editors` in the output — **no transformation, no rewriting, no overwriting of your manual `note` text or `picked_at` dates.**

Concretely:

- `editors.json` is loaded once per `stats` pipeline run.
- Picks are forwarded verbatim into the output shape.
- A pick whose `library` doesn't match any known library in the loaded `libraries.json` is gracefully skipped at render time — see the fallback loop in `pickLibraryForEditor` at `index.html:1140-1146` — so a typo never throws, it just causes the next-newest pick (or the previous one, etc.) to surface.
- A read failure (missing or malformed file) returns `[]` from `readEditorsFile`, not an error.

### UI rendering

Implemented in `index.html:1135-1243`. Per editor:

1. `pickLibraryForEditor(editor)` ([index.html:1135](../index.html)) sorts `editor.picks` by `picked_at` descending and returns the **first pick whose `library` name resolves in the loaded library set**. Older picks are walk-through fallbacks — useful for graceful degradation when a newer pick's library temporarily drops out of the index.
2. The matching `Library` is rendered with `renderPickCard(lib, { kind: 'editor' })` ([index.html:1117](../index.html)).
3. Up to 6 editors display (`editorPicks.slice(0, 6)` at `index.html:1173`).
4. Clicking the card opens the standard library detail modal (`openLibraryDetail` at `index.html:1123`).

The editor's `name`, `bio`, and the per-editor pick history are not embedded in the card itself — they live on the library detail page. The card stays minimal: library name, version, author, stars, short description, category, with a teal left-edge accent (see [On-page attribution](#on-page-attribution)).

## Stream 2: Themed Auto-Picks (self-rotating)

### What it is

Static theme definitions with selection criteria. Each week the pipeline queries the full library DB through `pickByTheme` ([`theme-picker.ts:49`](../pipeline/src/transforms/theme-picker.ts)) and ranks matches by stars → recency → name. The result set **rotates weekly** because it depends on the live `libraries.json`, which the pipeline refreshes daily.

Themes are entirely declarative — you describe the criteria, the pipeline does the rest.

### File: `themes.json` (project root)

Schema (see `pipeline/src/types.ts` lines 101-113):

```ts
interface Theme {
  id: string;                          // DOM id fragment (e.g. "themed-iot")
  title: string;                       // Display heading
  criteria: ThemeCriteria;
  count: number;                       // Max number of libraries to surface
}

interface ThemeCriteria {
  categories_any?: string[];           // Match if lib.category ∈ list (case-insensitive)
  architectures_any?: string[];        // Match if lib.architectures ∩ list ≠ ∅
  min_stars?: number;                  // Drop libs below this github_stars
  exclude_categories?: string[];       // Drop libs whose category ∈ list
}
```

Live example from the current `themes.json`:

```json
{
  "id": "iot",
  "title": "IoT",
  "criteria": {
    "categories_any": ["Communication", "Wireless", "Network"],
    "architectures_any": ["esp32", "esp8266", "rp2040"],
    "min_stars": 10
  },
  "count": 8
}
```

### Built-in themes

Five themes ship by default:

| Theme | Criteria |
|---|---|
| `iot` | categories in {Communication, Wireless, Network} AND architectures intersect {esp32, esp8266, rp2040} AND stars ≥ 10 → top 8 |
| `sensors` | categories in {Sensor, Sensors} AND stars ≥ 5 → top 8 |
| `display` | category in {Display} AND stars ≥ 5 → top 8 |
| `motor-control` | categories in {Device Control, Motor Control} AND stars ≥ 5 → top 6 |
| `communication` | category in {Communication} AND stars ≥ 5 → top 8 |

### Adding a new theme

Append a new object to the `themes` array in `themes.json`. Copy-paste template:

```json
{
  "themes": [
    ... existing themes ...,
    {
      "id": "audio",
      "title": "Audio & Sound",
      "criteria": {
        "categories_any": ["Audio", "Sound"],
        "min_stars": 5,
        "exclude_categories": ["Uncategorized"]
      },
      "count": 8
    }
  ]
}
```

Constraints:

- `id` must be unique and DOM-safe (lowercase, hyphens).
- All criteria fields are optional and **combine with AND**. A library only passes if it satisfies every present criterion.
- Comparison is case-insensitive (`theme-picker.ts:6-13`, `20-26`).
- `count` is clamped to `>= 0` (negative values are coerced to 0).
- `count` of 0 means "define but render nothing this week" — handy for soft-disabling.

### How the pipeline handles it

`buildPicksJson` runs `pickByTheme` for every theme and stores results as `themes[theme.id]: Library[]` ([`build-picks-json.ts:119-122`](../pipeline/src/output/build-picks-json.ts)). The pipeline uses raw `JSON.parse` with a try/catch fallback, so a malformed theme or criterion silently yields `[]` instead of crashing the build.

Within `pickByTheme`:

1. **Filter.** For each library, walk the criteria fields in order; skip if any required check fails. Empty `categories_any` / `architectures_any` arrays are treated as "no constraint" (the field is skipped — see `theme-picker.ts:74-94`).
2. **Sort.** Stars desc → `github_updated_at` desc → name asc ([`theme-picker.ts:97-107`](../pipeline/src/transforms/theme-picker.ts)). This is the same tiebreaker stack used everywhere else in the picks system, which keeps results stable week-over-week when stars tie.
3. **Limit.** Slice to `theme.count` (`theme-picker.ts:109-110`). Real-world output may be smaller if the filter rejects more libraries than `count`.

### Sort order (canonical)

```
stars desc  →  github_updated_at desc  →  name asc
```

## Stream 3: Computed Picks (algorithmic)

### What it is

Self-updating picks derived entirely from `output/libraries.json`, `output/changes.json`, and per-week trending deltas. No human input — the whole section regenerates every weekly pipeline run.

### Sections

| Section | Source | Rule |
|---|---|---|
| New This Week | `changes.json.new_libraries` | Top 8 by `name` desc |
| Updated This Week | `changes.json.updated_libraries` | Top 8 by `library.name` desc; renders `old → new version` |
| Hidden Gems | All libraries | `github_stars < 20`, `github_updated_at` within last 90 days, non-empty description, has category |
| Trending | Weekly star-delta scores | Top 20 by 7-day delta desc |
| Forgotten Classics | All libraries | `github_stars > 100`, no update for > 365 days (or no update at all) |

All five are emitted under `picks.computed` in `output/picks.json` ([`build-picks-json.ts:78-105`](../pipeline/src/output/build-picks-json.ts)).

### Computed Pick rules

Each rule lives in [`pipeline/src/transforms/computed-picks.ts`](../pipeline/src/transforms/computed-picks.ts). Limits default to 20 each unless overridden.

#### `hiddenGems` ([computed-picks.ts:57](../pipeline/src/transforms/computed-picks.ts))

A library qualifies iff **all four** hold:

- `lib.github_stars < 20`
- `lib.github_updated_at` is within the last 90 days (`ageDays(updated_at, now) < 90`)
- `lib.sentence.trim()` or `lib.paragraph.trim()` is non-empty
- `lib.category.trim()` is non-empty

Sort: `stars ascending` (fewest stars = "best gem") → `updated_at desc` tiebreaker. Limit 20.

#### `trending` ([computed-picks.ts:93](../pipeline/src/transforms/computed-picks.ts))

- Driven by `trendingScores: Record<string, number>` keyed by `repository_name`.
- The score is computed as **`state.previous_stars[repo] → current github_stars` delta** each weekly run.
- Sort: `score desc` → `current stars desc` → `updated_at desc`. Limit 20.
- **Empty until weekly stats has run at least once** — the score map is only populated by the `stats` pipeline command ([`scripts/pipeline.ts:496-540`](../scripts/pipeline.ts)), so a fresh clone shows nothing in the trending row until the first weekly cron tick.

#### `forgottenClassics` ([computed-picks.ts:134](../pipeline/src/transforms/computed-picks.ts))

- `lib.github_stars > 100`
- `lib.github_updated_at` is null **or** older than 365 days (`age === null || age > 365`)

Sort: `stars desc` → `name asc`. Limit 20.

#### `mostDependedOn` ([computed-picks.ts:169](../pipeline/src/transforms/computed-picks.ts))

- Walks every library's `depends[]` array, counts how many libraries list each name as a dependency.
- Sort: count desc → `stars desc` → `name asc`. Limit 20.
- **Not displayed on the home page** — exposed only under `stats.json` (`output/stats.json`). It lives in the picks output for downstream consumers, but the frontend `displayCuratedDiscoveries` does not currently render it (`index.html:1149-1243` doesn't reference it).

## Output: `output/picks.json`

### Schema

Shape mirrors `PicksOutput` from [`pipeline/src/types.ts:123`](../pipeline/src/types.ts):

```ts
interface PicksOutput {
  generated_at: string;                            // ISO timestamp of build
  editors: Editor[];                               // verbatim from editors.json
  themes: Record<string, Library[]>;              // theme.id → ranked libraries
  computed: {
    new_this_week: Library[];                      // top 8 by name desc
    updated_this_week: UpdatedLibraryChange[];     // top 8 by library.name desc
    hidden_gems: Library[];                        // <= 20
    trending: Library[];                           // <= 20 (empty until first weekly stats run)
    forgotten_classics: Library[];                 // <= 20
  };
}
```

Where `Library` is the canonical shape from `pipeline/src/types.ts:3-27` (the same shape used in `output/libraries.json`).

### Who reads it

- The pipeline's `stats` command **writes** the file ([`scripts/pipeline.ts:541`](../scripts/pipeline.ts)).
- `index.html` **loads** it on bootstrap via `loadPicks()` ([index.html:1106-1115](../index.html)), which is fetched with a cache-busting `?v=${Date.now()}` so a freshly built picks file is always picked up.
- If the fetch fails (404, parse error), the entire `#curatedDiscoveries` section stays hidden — the page degrades silently to just the main library grid.

### Frontend rendering

Three row groups, all built inside `displayCuratedDiscoveries` ([index.html:1149-1244](../index.html)):

| Row group | DOM target | Source from `picksData` | Cap |
|---|---|---|---|
| Editor Picks | `#editorPicksRow` / `#editorPicksGrid` | `picksData.editors` → `pickLibraryForEditor` → first matching pick | 6 |
| This Week (New + Updated) | `#computedRow` / `#computedGrid` | `picksData.computed.new_this_week` (badge `new`) interleaved with `updated_this_week` (badge `updated`) | 6 + 6 |
| Themed rows | `#themedRows` (one `.themed-row` per theme) | `picksData.themes[themeId]` → `renderPickCard` | 8 per theme |

Card HTML is produced by `renderPickCard(lib, attribution)` ([index.html:1117](../index.html)). `attribution` is one of:

```js
{ kind: 'editor' }                   // teal left-edge accent, no badge
{ kind: 'themed' }                   // dark-gray left-edge accent, no badge
{ kind: 'computed', badge: 'new' }     // small teal "NEW" top-right
{ kind: 'computed', badge: 'updated' } // small orange "UPDATED" top-right
```

The total `picksData` contributes to a header count: `#curatedCount` shows `N highlighted` ([index.html:1239-1240](../index.html)).

## On-page attribution

The card type and badge shape are driven entirely by CSS classes. You can
identify any card by inspecting its class list.

Pick attribution no longer lives on the left edge of the card (the previous
"left spine" color cue was removed in the catalog-card redesign). All
attribution now uses a small **corner badge** plus a matching **dot** next
to the call-number row at the top of the card.

| Stream | Card class | Visual marker |
|---|---|---|
| Editor Picks | `.library-card.pick-editor` | `.pick-badge.editor` (teal) top-right + teal pick-dot next to call number |
| Themed Picks | `.library-card.pick-themed` | `.pick-badge.themed` (dark gray) top-right + dark-gray pick-dot |
| Computed — New | `.library-card.pick-computed` + `.pick-badge.new` | Teal `NEW` chip top-right + black pick-dot |
| Computed — Updated | `.library-card.pick-computed` + `.pick-badge.updated` | Orange `UPDATED` chip top-right + black pick-dot |

The `.pick-badge` class defines the badge geometry (absolute positioned,
8 px from top-right, uppercase, 9 px font). The `.editor`, `.themed`,
`.new`, and `.updated` modifiers set the fill and border colors. The
`.pick-dot` element is a 6 × 6 px circle that anchors vertical scans and
provides a screen-reader-friendly visible marker for the pick kind.

No "Picked by X" labels appear on cards themselves — the editor `name` and
`bio` are exposed in the library detail page so the home grid stays
compact.

## FAQ

### Why doesn't my new editor pick appear?

The most common causes, in descending frequency:

1. **`library` name doesn't match.** The match in [`pickLibraryForEditor`](../index.html#L1141) is case-insensitive equality against `libraries[i].name`. Look up the exact name in `output/libraries.json` (search the file) — author capitalization, trailing spaces, and punctuation matter at the exact-match level even though case doesn't.
2. **Library not in the DB yet.** If `editors.json` references a library the pipeline doesn't know about (no entry in `output/libraries.json`), the loop at `index.html:1140-1146` falls through to your next-newest pick. Pick a library that exists today, then re-aim your pick later via PR when the library appears.
3. **Weekly hasn't run since your PR merged.** The pipeline writes `output/picks.json`; the static site reads it as-is. Until the next weekly cron (Sunday 04:00 UTC) or until someone manually runs `node --experimental-strip-types scripts/pipeline.ts stats`, your entry won't show up.

### Why is a theme showing fewer than N picks?

`pickByTheme` filters first, then sorts, then slices to `theme.count` (`theme-picker.ts:72-110`). If fewer than `count` libraries satisfy the criteria, the theme shows that smaller number — no padding is added. To get more results, **loosen a criterion** (drop `min_stars`, broaden `categories_any`, remove `exclude_categories`).

### How do I disable a theme temporarily?

Two options:

1. **Soft-disable.** Set `"count": 0` in the theme entry. The row is emitted with `[]` and the rendering loop at `index.html:1222` skips empty theme rows entirely — clean hide, easy to re-enable later.
2. **Hard-remove.** Delete the entry from the `themes` array. Use this for permanent retirement; the theme id is gone from `picks.json` immediately on next build.

Option 1 is recommended for "this theme isn't useful right now" — your git history and PR diff stay readable.

### Can editors be removed?

Yes — delete the editor's object from the `editors` array in `editors.json`. The frontend gracefully renders one fewer row ([index.html:1185-1187](../index.html) hides the whole `#editorPicksRow` when zero editors resolve). Note the editor's previous picks still live in git history if you ever want to resurrect them.

To replace an editor entirely while keeping the slot, edit the existing object rather than deleting and re-adding (so any preserved picks aren't orphaned): update `id`/`name`/`url`/`bio` in place and clear or refill `picks`.

### Where is the trending row — mine is empty?

The `trending` section requires at least one `stats` pipeline run to have completed (it reads `trendingScores` populated from `state.previous_stars` deltas). On a fresh clone or immediately after enabling the workflow, the row will be empty until the first weekly run. After that it stays populated and rotates weekly. See [`trending` rule](#trending) above for the precise mechanic.

### Why don't I see a "Most Depended On" row?

By design — see [the rule](#mostdependedon). It's computed and emitted to `output/stats.json` for downstream consumers but the home page UI does not render it. If you want to surface it, you'd add a new row group in `displayCuratedDiscoveries` mirroring the themed-rows pattern ([index.html:1217-1234](../index.html)).
